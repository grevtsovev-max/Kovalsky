# Архитектура агента Kovalsky

## Реализованная система

Kovalsky — одно Python-приложение с последовательным конвейером обработки новостей. В нём есть специализированные AI-этапы, но нет автономных агентов, которые общаются друг с другом или сами выбирают инструменты. Оркестрация сейчас реализована обычным кодом; LangGraph не используется.

### Статусы материалов

- `PENDING` — материал сохранён и ожидает обработки.
- `PRIMARY_RETRY`, `AI_RETRY`, `WAITING_CONFIRMATION` — обработка приостановлена с ограниченным повтором.
- `NEW_STORY`, `UPDATE_CANDIDATE` — создан сюжет или найдено существенное обновление; пост ещё проходит редакционный допуск.
- `DUPLICATE`, `NOISE`, `STALE`, `UNDATED`, `BASELINE_SKIPPED`, `STORE_ONLY`, `REJECTED` — обработка завершена без отдельной публикации.
- `ERROR` — отдельная запись в журнале решений о техническом сбое; это не статус материала.

Статусы поста и доставки отдельны. Пост проходит `PENDING → PUBLISHED` или `REJECTED`; попытка доставки проходит `PREPARED → SENDING → SENT → CONFIRMED` либо завершается `FAILED`/`UNKNOWN`. Неопределённая отправка блокирует слепой повтор.

| Исходное состояние материала | Следующий путь | Ограничение / причина |
| --- | --- | --- |
| `PENDING` | Повторная обработка → один из hold-, story- или terminal-исходов | Новая или изменённая версия материала |
| `PRIMARY_RETRY` | Повторная обработка → hold-, story- или terminal-исход | Не получен читаемый пригодный материал; попытки ограничены |
| `AI_RETRY` | Повторная обработка → hold-, story- или terminal-исход | AI-анализ не завершён или отложен |
| `WAITING_CONFIRMATION` | Повторная редакционная проверка → terminal/story-исход либо ещё одна отсрочка | Не более трёх автоматических редакционных повторов |
| `NEW_STORY`, `UPDATE_CANDIDATE` | Сохранённый пост-кандидат → финальный допуск → доставка либо отказ | Положительный исход обработки сам по себе не означает публикацию |
| Любой сохранённый статус | `PENDING` при обнаружении новой версии материала | Старый снимок и старое решение остаются в истории |
| `REJECTED` | Повтор только через предусмотренное исправление/повторную очередь | Не является общей ручной командой на переоткрытие |
| Любой этап | Отдельная запись `ERROR` при пойманном исключении | `ERROR` — запись аудита, а не значение `items.disposition` |

Эта таблица фиксирует наблюдаемые пути, но пока не является исполняемым валидатором: изменения `items.disposition` остаются в нескольких ветках `core.py` и в коде очереди восстановления. Централизация переходов — следующий кодовый шаг.

## Уже реализованные гарантии

- Предварительный AI-отбор не разрешает публикацию.
- Источник читается, а проверки повторяются до ограниченного числа раз.
- Решение хранится вместе со снимками версий редакционных и системных правил.
- Финальный допуск повторно проверяется непосредственно перед отправкой.
- Журнал доставки фиксирует попытку до сетевого вызова и не повторяет неизвестный результат вслепую.

## Изменение этого этапа

При ошибке обработки запись `ERROR` теперь по возможности связывается с уже сохранённым `item_id` и `story_id`. В запись также попадают трасса пройденных этапов и результат предварительного AI-отбора. Поэтому история сбоя может отображаться рядом с историей конкретного материала, а не только существовать отдельной несвязанной строкой.

## Следующие улучшения

1. Свести разрешённые переходы статусов в проверяемую таблицу и постепенно подключить её в местах изменения `items.disposition`.
2. Проверить, что ключевые промежуточные решения переживают сбой процесса; дополнить журнал только там, где сейчас есть разрыв, не создавая второй параллельной истории.
3. Выделить границы сбора, отбора, чтения, анализа, памяти и доставки в узлы с явными входами/выходами, сохраняя текущую логику и SQLite.
4. Показывать безопасные статусы узлов, время и число попыток в панели.
5. После этого решить, даёт ли LangGraph достаточно ценности для долгих возобновляемых задач, чтобы оправдать новую зависимость и эксплуатационный слой.
