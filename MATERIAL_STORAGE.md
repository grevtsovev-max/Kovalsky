# Хранение и перенос материалов

## Где находятся данные

Рабочий файл конфигурации задаёт `newsroom.database`: это база SQLite с материалами,
редакционными решениями, очередью и подтверждениями отправок. Полные новые прочитанные
статьи сохраняются в `reader.archive_directory`. Если параметр отсутствует, используется
папка `materials` рядом с файлом базы. Относительные пути разрешаются от рабочей
директории процесса; для производственной установки задавайте абсолютные пути вне
каталога выпуска. Фактические адреса и секреты находятся только в закрытой конфигурации.

В архиве файл имеет вид `первые-два-символа-ID/ID-материала/ID-версии.json`.
ID материала — SHA-256 URL, ID версии — SHA-256 содержимого снимка без времени чтения.
JSON содержит URL, название источника, заголовок, даты, полный извлечённый текст,
способ чтения и сведения о прочитанном первоисточнике. Это извлечённый материал,
а не гарантия наличия всех сведений на сайте. Текст, отсутствовавший в прежних записях,
автоматически не восстанавливается. Новые версии не удаляют старые.

## Резервное копирование

Сохраняйте вместе базу, архив materials и закрытые настройки/необходимые файлы доступа.
Базу работающего приложения копируйте через SQLite Online Backup API, а не простым
копированием одного файла: активная база может использовать WAL. Для согласованного
снимка сначала остановите сбор, редакторский бот и кабинет, выполните SQLite backup,
скопируйте архив и настройки, затем верните службы в работу. Резервную копию храните
также на отдельном носителе или сервере. Проверяйте восстановление на изолированной
установке с отключённой доставкой Telegram.

## Переподключение

1. Восстановите **ту же базу**, включая историю публикаций, очередей и доставки.
2. Восстановите папку materials без изменения её внутренней структуры.
3. Укажите новые абсолютные пути в `newsroom.database` и `reader.archive_directory`.
4. Восстановите закрытые настройки и права доступа владельца приложения.
5. Проверьте `PRAGMA integrity_check`, наличие снимков и историю доставки до запуска.
6. Остановите старую установку перед включением новой: одновременно должен работать
   один производственный конвейер. Не создавайте пустую базу вместо восстановленной.

## Jina Reader

Jina — отдельный извлекатель, не хранилище и не разрешение на публикацию.
Адаптер использует только собственный HTTP endpoint на loopback, получает HTML
после браузерного исполнения и передаёт его штатному разбору источников.
Настройка `[reader]`: `jina_enabled = true`, `jina_endpoint = "http://127.0.0.1:3000"`.
По умолчанию адаптер выключен. При тайм-ауте штатного чтения резерв сразу не запускается.

Перед включением сервиса проверьте: ограничение памяти/CPU и числа браузеров;
запрет доступа браузера к локальным/частным сетям и metadata endpoints на уровне
сети (в том числе после DNS и редиректов); публикацию порта только на loopback;
чтение реальных источников, их дат и ссылок без CAPTCHA; отказ при неполном результате.
Контейнер upstream: `ghcr.io/jina-ai/reader:oss`, HTTP/1.1 порт 8081.
Для выпуска фиксируйте проверенный digest образа. Самостоятельный Reader по умолчанию
не кеширует ответы и не ограничивает запросы; эти ограничения нужно настроить отдельно.

Если собственного сервиса нет, адаптер не следует включать. Облачный Jina автоматически
не подставляется. Ошибка записи архива означает ошибку чтения: материал не считается
успешно сохранённым и не получает обход публикационных проверок.

## Воспроизводимое развёртывание Reader

В `ops/jina/` сохранены Dockerfile, шаблон systemd-службы и настройка сети.
Образ зафиксирован digest официального upstream. В собственном образе исправлен
один вызов SaaS-проверки подписки для браузерного HTML: OSS-образ иначе возвращает
500 «Not implemented». Другие проверки и механизмы чтения не изменяются.
Сборка: `docker build -t kovalsky-jina:verified ops/jina`.
Служба публикует только локальный порт, ограничивает память, CPU и число процессов.
Сетевой скрипт запрещает контейнеру доступ к частным IPv4-сетям и входящие
подключения к серверу; Docker-сеть не должна получать IPv6 без отдельной защиты.
Перед запуском на другом сервере проверьте отсутствие конфликта подсети шаблона.

## Облачный резерв

Облачный ключ хранится в отдельном закрытом файле, указанном в
`reader.jina_api_key_file`, либо в `JINA_API_KEY`. Используется только официальный
HTTPS endpoint `r.jina.ai`; редиректы самого endpoint запрещены. Ключ не сохраняется
в архиве. Облако получает URL общедоступного источника и возвращает очищенный текст;
параметр DNT запрещает облачное кеширование/журналирование согласно документации API.
Ответ проходит обычный разбор и сохраняется вместе с исходным `reader_content`.

Лимиты задают `jina_cloud_daily_requests` и `jina_cloud_request_tokens`.
`jina-cloud.sqlite3` рядом с основной базой хранит попытки и известный расход:
копируйте её также при переносе, чтобы не сбросить суточный лимит.
`jina_cloud_hosts` задаёт сайты, для которых после ошибки обычного чтения сначала
используется облако. Прокси выключены по умолчанию; включение `jina_cloud_proxy`
может увеличить расход. Никакого автоматического пополнения приложение не выполняет.
